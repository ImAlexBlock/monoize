## 先看日誌

修改設定之前，先開啟儀表板中的**日誌**。每個失敗請求的行都顯示錯誤碼、HTTP 狀態和每次失敗的上游嘗試。開啟[請求擷取](/zh-TW/docs/request-logs)可以檢查上游的完整封包。

## 認證錯誤

### `401 unauthorized`

1. 確認金鑰以 `sk-` 開頭且完整。
2. 在**令牌管理**中確認金鑰已啟用且未過期。
3. 確認金鑰所屬的使用者帳戶已啟用。
4. 確認請求標頭格式：`Authorization: Bearer sk-...` 或 `x-api-key: sk-...`。

### `403 model_not_allowed`

金鑰開啟了模型限制，且請求的模型不等於任何條目。把精確的邏輯模型名加入金鑰的模型列表，或關閉模型限制。

### `403 ip_not_allowed`

用戶端 IP 不在金鑰的 IP 白名單中。新增該位址或 CIDR 網段，或清空白名單。Monoize 位於反向代理之後時，確認代理轉發了真實的用戶端 IP。

## 路由錯誤

### `502 upstream_error`

所有符合條件的路由都失敗，或沒有路由服務該模型。按以下順序檢查：

1. **路由不存在。** 確認已啟用的 Provider 擁有一個已啟用的 Channel，並用完整的 Billing Profile 對應該模型。
2. **群組無交集。** 金鑰的群組必須與 Provider 至少共享一個群組。參見 [API 金鑰](/zh-TW/docs/dashboard/api-keys)。
3. **所有 Channel 不健康。** 斷路器在冷卻期內跳過不健康的 Channel。檢視日誌行中的失敗嘗試，找到根本的上游錯誤。
4. **倍率上限。** 設定了 `max_multiplier` 的金鑰會跳過價格高於上限的模型條目。

## 計費錯誤

### `402 insufficient_balance`

使用者餘額或金鑰的子帳戶餘額為零或負數。請在**使用者**中儲值。保留獨立餘額的舊金鑰會繼續從其餘額扣款，直到歸零或刪除；新金鑰不再提供子帳戶選項。

### `402 api_key_spend_limit_reached`

金鑰的某個消費限額視窗已用盡。開啟金鑰的編輯對話框，提高或清空對應限額。小時視窗持續滾動；每日視窗在 UTC 零點重置。

### 費用看起來不對

費用 = 所選 Billing Profile 費率 × 有效倍率。先檢查 Provider 預設 Profile 和倍率，再檢查模型的 Profile 與倍率覆寫。

## 串流問題

### 串流在回應中途停止

第一個回應位元組之後，Monoize 絕不切換上游。中途斷掉的串流反映的是上游故障。檢視日誌行，並開啟擷取檢視上游原始幀。

### 用戶端拒絕超長 SSE 幀

某些用戶端限制 SSE 幀長度。在服務的 Provider 上新增 `stream_split_sse_frames` 變換。參見[串流：拆分超長 SSE 幀](/zh-TW/docs/transforms/stream_split_sse_frames)。

### 用戶端在長思考階段後回報傳輸解碼錯誤

錯誤文字為 `Transport error: error decoding response body`。Monoize 在每個 SSE 回應上傳送 `Cache-Control: no-cache` 和 `X-Accel-Buffering: no`。仍然緩衝或壓縮 `text/event-stream` 的反向代理可能截斷串流。為 Monoize 的 location 停用代理緩衝。在 nginx 中設定 `proxy_buffering off`。確認代理不會 gzip 該事件串流。

### 上游要求串流請求

新增 `stream_force` 變換，強制向上游發送 `stream: true`。用戶端請求非串流時，Monoize 仍然向用戶端返回非串流回應。

## 協議轉換問題

### `400 empty_input_after_conversion`

傳送非空訊息或完整對話歷史。此錯誤表示轉換後，可用的 Chat Completions 或 Responses Channel 沒有可傳送的訊息。

透過 Chat Completions 傳送工具結果時，同時包含對應的工具呼叫。僅在支援伺服器端狀態的 Responses 上游使用 `previous_response_id` 或 `conversation`。Monoize 為 Responses 上游保留這些參照和已儲存的 `prompt` 物件。

Monoize 跳過訊息為空的 Channel，並檢查其餘 Channel。若全部為空，它回傳此錯誤，不呼叫上游，也不切換模型。串流請求收到錯誤事件。此檢查無法恢復缺失的歷史。重現前啟用請求擷取，以定位內容遺失的位置。

### `400 invalid_request` 提示 `does not support thinking.type=adaptive`

完整訊息是 `Messages model <名稱> does not support thinking.type=adaptive`。Monoize 在發出請求前校驗每個已編碼的 Messages 請求。它返回該錯誤，並且不呼叫任何上游。

Claude Code 在 `/v1/messages` 請求中發送 `thinking: { "type": "adaptive" }`。Monoize 為 `messages` 上游保留該物件。上游模型名必須表示支援 adaptive 的 Claude 模型。小寫後的名稱必須包含 `claude`，或以 `opus-`、`sonnet-`、`haiku-` 開頭。`DeepSeek/DeepSeek-V4-Pro` 這類名稱不滿足條件，因此校驗拒絕該請求。

採用以下任一修復方式：

1. **改用 Chat Completions 發送該模型。** 把 Channel 類型設為 `chat_completion`。或者在 Provider 上新增一條 **API 類型覆蓋規則**，把該模型模式映射到 `chat_completion`。規則模式比對用戶端發送的邏輯模型名，不是 `redirect` 目標。Monoize 隨後按上游模型族編碼推理控制欄位。
2. **只把 Claude 模型名重定向到 Claude 模型。** 檢查 Channel 的模型映射。把支援 adaptive 的 Claude 名稱 `redirect` 到其他模型族時，用戶端的 Claude 專屬控制欄位仍留在請求中。參見 [Provider 與 Channel](/zh-TW/docs/dashboard/providers-and-channels)。
3. **在用戶端關閉擴展思考。** 不含 `thinking` 物件的請求對非 Claude 模型可以通過校驗。含 `thinking.type=disabled` 的請求同樣可以通過。

對稱情形返回 `does not support thinking.type=enabled; use adaptive`。當用戶端發送手動 `budget_tokens`，而上游模型是 Opus 4.7 及更高、Sonnet 5 及更高、Fable 5 或 Mythos 5 時，出現該錯誤。修復方式相同。

### 轉換後推理內容消失

某些上游用非標準欄位返回推理內容。使用推理類變換還原或改寫。從[變換](/zh-TW/docs/transforms)開始。

### 提供商私有欄位沒有到達上游

跨協議族轉換會移除沒有安全目標表示的提供商私有巢狀欄位。使用 `field_set` 變換為某個 Provider 重新寫入欄位。

### 用戶端拒絕工具呼叫中的 `4338.0` 這類數字

部分上游在工具呼叫參數裡把整數寫成 JSON 浮點數。Codex 的 `write_stdin` 把 `session_id` 解析為整數，並拒絕 `4338.0`。Monoize 在把回應發給用戶端之前，會把工具呼叫參數中的整數值浮點數改寫為 JSON 整數。此改寫不需要變換規則。

## 儀表板存取

### 管理員密碼遺失

另一個 `super_admin` 可以在**使用者**中重設密碼。沒有其他 `super_admin` 時，直接在資料庫中重設。

### 第一個帳戶不是管理員

第一個註冊的帳戶成為 `super_admin`。此規則只生效一次。之後的帳戶預設為 `user`。
