## Store を開く

`/dashboard/store` で **Store** を開きます。**残高**、**プラン**、または**コード引き換え**を選択します。

![Store](/images/en/store.webp)

通貨コントロールで CNY または USD を表示します。この操作は、残高、今月の使用量、価格、ボーナス、受取額、プラン上限額を同時に更新します。

Monoize は USD と CNY の換算にすべて固定レート 1 USD = 6.72 CNY を使います。市場レートが変わっても残高は変わりません。

## 残高をチャージする

1. チャージ商品を選択するか、カスタム金額を入力します。
2. チャージ額、ボーナス額、受取額を確認します。
3. 有効な支払い Channel を 1 つ選択します。
4. 注文を作成します。

Monoize は Provider に接続する前に支払い試行を保存します。Stripe はホスト型 Checkout ページを開きます。

EPay は選択した決済方式ごとに 1 つのアクションを返します。QR ペイロードは支払いダイアログに読み取り可能なコードを表示します。支払い URL は、選択後に遷移するアクションを表示します。EPay は CNY の注文のみを受け付けます。USD の注文には Stripe を使用します。

Provider の結果が不明な場合は、別の支払い試行を作成しないでください。Monoize が既存の支払い試行を照合するまで待ちます。

Checkout の終了後、Store は注文を 2 秒ごとに確認します。支払いと履行の完了、注文の終了、または注文の期限切れで確認を停止します。

`/dashboard/orders` で注文を確認します。支払い状態と履行状態を個別に確認します。

Monoize は Channel の支払いを検証した後にのみ残高を付与します。管理者は未払いの注文を支払い済みまたは履行済みに変更できません。

## Stripe コールバックを設定する

Stripe Webhook エンドポイントを `https://lynshen.org/api/store/callbacks/{channel_id}` に設定します。`{channel_id}` を Stripe Channel ID に置き換えます。

`checkout.session.completed` と `checkout.session.async_payment_succeeded` を購読します。エンドポイント署名シークレットを暗号化された Stripe 認証情報に保存します。

## EPay を設定する

1 つの EPay Channel が Alipay 方式と WeChat Pay 方式の両方を提供します。

EPay 非同期通知 URL を `https://lynshen.org/api/store/callbacks/{channel_id}` に設定します。`{channel_id}` を EPay Channel ID に置き換えます。このエンドポイントは仕様どおりの `GET` 通知を受け付けます。

Store Management でゲートウェイのベース URL、加盟店 ID、加盟店キーを保存します。Alipay 方式、WeChat Pay 方式、またはその両方を有効にします。ゲートウェイのベース URL は `/` で終わる必要があり、ループバック、リンクローカル、プライベートアドレスを指してはいけません。

Monoize は各リクエストに署名します。`sign`、`sign_type`、空の値を除外し、フィールドを ASCII 順に並べ、小文字の MD5 を計算します。署名、加盟店 ID、注文番号、CNY の分単位の金額、期待する決済方式を検証し、支払い状態の遷移がコミットされた後だけ `success` を返します。

Channel 行で **EPay の決済方式**を開き、各方式の公開名、並び順、有効状態を設定します。ここで無効にした方式は Store に表示されません。

## プランを購入する

プランと支払い Channel を選択します。1 つのプランに複数の上限期間を同時に適用できます。期間には、5 時間、12 時間、日、週、月、または任意の整数時間を指定できます。

Monoize はプラン上限額を CNY で保存します。Store は、四捨五入した整数の CNY または USD 金額を表示します。

## SQLite でプランを有効にする

SQLite のクォータ Gate を変更する前に、Monoize アプリケーションを停止します。`MONOIZE_DATABASE_DSN` に対象の SQLite データベースを設定します。

合格した演習 manifest を `next` スロットにインポートします。

```bash
monoize-store-ops quota-gate import --slot next --manifest ./quota-manifest.json
```

コマンド出力から互換性 fingerprint を確認します。新しいアプリケーションバージョンを起動する前に、インポートした manifest を昇格します。

```bash
monoize-store-ops quota-gate promote --expected-fingerprint <fingerprint>
```

このコマンドは、PostgreSQL、サイズ超過の manifest、不正な JSON、現在の SQLite 環境と一致しない manifest を拒否します。

## コードを引き換える

**コード引き換え**に未使用のコードを入力します。コードは残高を追加するか、プランを有効にします。引き換えでは支払い Channel を使用せず、注文も作成しません。

## Store を管理する

管理者は `/dashboard/store-admin` を開きます。4 つのタブで商品、支払い Channel、注文、引き換えコードを管理します。

- CNY と USD のカスタムチャージ範囲を個別に設定します。
- EPay、Stripe、または HTTP 下書き Channel を追加します。組み込みアイコン、HTTPS 画像 URL、またはアップロード画像を使用します。
- 既存の EPay または Stripe Channel を開きます。すべての認証情報と現在の管理者パスワードを入力します。**認証情報を置換**を選択します。Monoize は新しいバージョンを暗号化し、以前のバージョンと Channel を無効にします。
- EPay Channel 行で **Governance** を開き、**EPay の決済方式**を選んで Alipay 方式と WeChat Pay 方式を設定します。
- Milestone 1 では HTTP Channel を無効のままにします。
- 支払い状態と履行状態を個別に確認します。手動完了操作は使用しません。
- 1 回に 1 から 20 個の単回使用コードを生成します。Monoize が平文コードを表示したときに保存します。
- **支払いチャネル**タブの上部から**プライバシー記録**と**データ保持**を開きます。
- EPay または Stripe の Channel 行で **Governance** を開きます。**決済コンプライアンス**、**加盟店ケイパビリティ**、**チャネル準備状況**、または **EPay の決済方式**を選びます。HTTP Channel 行にこの操作はありません。

## プライバシー記録を確認する

本番のチェックアウトとコールバックには、現行の承認済み Store プライバシー記録が必要です。再審査の間隔は 365 日を超えてはいけません。

`/dashboard/store-admin` で**商店管理**を開きます。**支払いチャネル**タブを選択します。**プライバシー記録**を選択します。

![Store privacy records](/images/en/store-privacy-records.webp)

一覧の各記録は、ポリシーバージョン、管轄区域、許可地域、承認状態、次回の再審査日を表示します。保存した記録は編集できません。

ポリシー更新を承認したら記録を追加します。次の値を入力し、**記録を追加**を選択します。

| 項目 | 有効な値 |
| --- | --- |
| **ポリシーバージョン** | 1 から 64 バイト |
| **管轄区域** | 1 から 128 バイト |
| **許可地域（カンマ区切り）** | 重複しない 1 から 32 個の値 |
| **法的根拠** | 1 から 512 バイト |
| **証跡 SHA-256 ダイジェスト** | 小文字の 16 進数でちょうど 64 文字 |
| **財務記録の保持日数** | 1 から 36500 |
| **期限切れ許可の保持時間** | 1 から 24 |
| **再審査までの日数** | 1 から 365 |

フォームは管轄区域と許可地域に `CN`、財務記録の保持に 2557 日（7 年）、期限切れ許可の保持に 24 時間、再審査までに 90 日を初期表示します。各値をポリシーが承認した値に置き換えます。

Monoize は審査者、承認時刻、次回の再審査日を設定します。Monoize はフォームに現れない 3 つの保持期間も固定します。コールバック本文は 30 日、ネットワークメタデータは 90 日、引換監査は 730 日です。

## チャネルのガバナンスを設定する

決済コンプライアンス、加盟店ケイパビリティ、準備状況が揃うまで、Channel は利用不可のままです。準備状況は現行の承認済みプライバシー記録を参照する必要があります。

![Store payment Channels](/images/en/store-governance.webp)

EPay または Stripe の Channel 行で **Governance** を開きます。

1. **決済コンプライアンス**を選択します。現行の Store 決済条件を確認し、管理者パスワードで確定します。Monoize はスコープ `compliance_confirm` の 5 分間の再認証許可を取得します。
2. **加盟店ケイパビリティ**を選択します。必要な各ケイパビリティについて、状態、環境、Provider 商品、証跡ダイジェスト、有効期限を記録します。
3. **チャネル準備状況**を選択します。**プライバシー記録**を選択します。署名付きコールバック試験に合格した後だけ**コールバック検証済み**を有効にします。対応通貨、チェックアウト動作、通貨ごとの金額範囲、ライセンス、実行、可用性の各証跡ダイジェスト、そして 1 から 90 日の有効期間を設定します。**保存**を選択します。

プライバシー記録が 1 件もない間、準備状況の保存操作は無効のままです。先に**プライバシー記録**で記録を追加します。

各 Channel 行は設定状態と実効状態を表示します。利用不可の Channel は、読みやすい理由ラベルと生の理由コードを表示します。例はプライバシー記録の不足、準備プロファイルの欠落や期限切れ、コールバック検証の未完了、決済条件未確認、ケイパビリティ検証の不足です。

## データ保持を理解する

Monoize は Store Primary で毎日 03:00 UTC に上限付きの保持ジョブを 1 回実行します。Replica はこのジョブを実行しません。各実行は開始時点で現行の承認済みプライバシー記録を使用します。

次の保持期間がすべての記録に適用されます。

- コールバック本文：30 日。
- ネットワークメタデータ（送信元 IP と User-Agent）：90 日。
- 引換コードの表示、コピー、エクスポートの監査：730 日。
- 期限切れ再認証許可のハッシュ：期限切れ後、**期限切れ許可の保持時間**が経過するまで。
- 財務記録：**財務記録の保持日数**。

1 回の実行は 5 つのデータクラスごとに、保持対象外のルート記録を最大 500 件まで検査して変更します。データクラスは `raw_callback_bodies`、`network_metadata`、`financial_records`、`redemption_audits`、`expired_reauth_grants` です。

最初の 2 つのデータクラスは行を削除せず、項目だけを消去します。実行は期限を過ぎたチャネルイベントの暗号化本文を消去し、90 日を過ぎたイベントの送信元 IP と User-Agent を消去します。イベント行、本文ダイジェスト、解析済みイベント、検証結果、投影状態は残ります。

財務ルート記録を 1 件削除すると、その支払い試行、イベント適用、返金、返金照会の再試行、報酬回収行、回収請求行も削除します。実行は有効なエンタイトルメントとその発行記録を残します。

各実行は 1 つのトランザクションで完了します。失敗するとその実行の削除をすべてロールバックします。変更のないデータに対して実行を繰り返しても、消去済みの項目は変わりません。前回の実行が候補を削除していても失敗しません。

支払いデータ、コールバック証跡、バックアップ、ログ、暗号鍵は、プライバシー記録の許可地域内にとどまります。証跡の読み取り、エクスポート、保持の上書き、法的保持の各操作は、実行者、役割、範囲、理由、時刻、結果を記録する変更不可のアクセス監査を書き込みます。

## 保持を手動で実行する

**商店管理**を開きます。**支払いチャネル**タブを選択します。**データ保持**を選択します。

![Store retention](/images/en/store-retention.webp)

ダイアログは連続失敗、チェックアウトの状態（**受付中**または**停止中**）、保持実行の件数、リーガルホールドの件数を表示します。保持期間を過ぎた記録は実行後に完全削除されることも示します。

**現在のパスワード**と**理由**を入力します。いずれかが空の間、実行ボタンは無効です。**保持を実行**を選択します。Monoize はスコープ `retention_operation` の 5 分間の再認証許可を取得し、上限付きの実行を 1 回開始します。

実行が既に進行中の場合、要求は HTTP `409` とコード `retention_run_active` を返します。成功した実行は連続失敗を 0 に戻します。失敗または中断した実行はこの値を 1 増やします。

## リーガルホールドを適用する

リーガルホールドは 1 つのデータクラスで指定した識別子の削除を停止します。**データ保持**ダイアログはリーガルホールドの件数を表示します。ここでリーガルホールドを作成することはできません。

`POST /api/dashboard/store/admin/retention/legal-holds` でリーガルホールドを作成します。この要求には管理者セッション、Store Primary、スコープ `legal_hold` の 5 分間の再認証許可が必要です。JSON 本文は `data_class`、`identifiers`、`reason`、`requesting_authority`、`requester_id`、`approver_role`、`expires_at`、`extends_hold_id` を含めます。

- `data_class` は 5 つの保持データクラスのいずれかにします。
- `identifiers` は重複しない 1 から 100 個の値を含めます。各値は最大 255 バイトです。
- `approver_role` は `privacy` または `legal` にします。
- `requester_id` は認証済み管理者と異なる値にします。その管理者が承認者です。
- `expires_at` は未来の RFC3339 時刻にします。
- 初回承認では `extends_hold_id` を `null` にします。延長は、データクラスと識別子が同一のリーガルホールドを参照し、より遅い期限を使用します。

リーガルホールドは、開始時刻が評価時刻以前で、評価時刻が期限より前の間だけ適用されます。期限を過ぎると操作なしで終了します。リーガルホールドは削除済みデータを復元しません。保存済みの保持行を更新、削除、再有効化、変更する操作はありません。延長は新しいリーガルホールドと新しい承認監査を追加します。

## チェックアウト停止を解除する

実行の失敗によって連続失敗が 3 に達し、チェックアウトがまだ停止していない場合、Monoize は重大な保持アラートを 1 件作成し、チェックアウトを停止します。

チェックアウトの停止中、新しい注文と新しい支払い試行は HTTP `503` とコード `store_retention_paused` を返します。既存の注文または終了状態の支払い試行に対する冪等な再送は、以前の結果をそのまま返すことがあります。コールバックの受信、照合、返金、保持の各操作は利用できます。

アプリケーションを再起動しても、カウンター、アラート、停止は保持されます。実行が成功しただけでは停止は解除されません。

停止を解除するには**データ保持**を開きます。ダイアログはチェックアウトの停止中だけ**証跡 SHA-256 ダイジェスト**の項目を表示します。送信すると現在のアラートを解除してチェックアウトを直ちに再開することも示します。**現在のパスワード**、**理由**、ダイジェストを入力します。パスワードと理由が空、またはダイジェストがちょうど 64 文字でない間、対応ボタンは無効です。**アラートを対応済みにする**を選択します。

Monoize は対応を記録し、アラートを対応済みにして、チェックアウトを再開します。対応は連続失敗の値を変更しません。その後に実行が失敗すると、再びチェックアウトを停止することがあります。有効で未対応のアラートがない場合、対応要求は HTTP `409` とコード `retention_containment_unavailable` を返します。
