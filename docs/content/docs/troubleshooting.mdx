## Diagnose with logs first

Open **Logs** in the dashboard before you change configuration. Each failed request row shows the error code, the HTTP status, and every failed upstream attempt. Enable [request capture](/en/docs/request-logs) to inspect the exact upstream payloads.

## Authentication errors

### `401 unauthorized`

1. Confirm the key starts with `sk-` and is complete.
2. Confirm the key is enabled and not expired in **Token Management**.
3. Confirm the owning user account is enabled.
4. Confirm the header format: `Authorization: Bearer sk-...` or `x-api-key: sk-...`.

### `403 model_not_allowed`

The key has model limits enabled and the requested model equals no entry. Add the exact logical model name to the key's model list, or disable model limits.

### `403 ip_not_allowed`

The client IP is not in the key's IP whitelist. Add the address or CIDR range, or clear the whitelist. When Monoize runs behind a reverse proxy, confirm the proxy forwards the real client IP.

## Routing errors

### `502 upstream_error`

All eligible routes failed, or no route serves the model. Check in this order:

1. **No route exists.** Confirm an enabled Provider has an enabled Channel that maps the model with a complete Billing Profile.
2. **Groups do not intersect.** The key's groups must share at least one group with the Provider. See [API Keys](/en/docs/dashboard/api-keys).
3. **All Channels unhealthy.** The circuit breaker skips unhealthy Channels during cooldown. Read the failed attempts on the log row to find the root upstream error.
4. **Multiplier cap.** A key with `max_multiplier` skips model entries priced above the cap.

## Billing errors

### `402 insufficient_balance`

The user balance, or the key's sub-account balance, is zero or negative. Top up the balance in **Users**. Legacy keys with an independent balance keep settling against it until drained or deleted; new keys have no sub-account option.

### `402 api_key_spend_limit_reached`

A spend-limit window on the key is exhausted. Open the key's edit dialog and raise or clear the limit. The hourly window rolls over continuously; the daily window resets at UTC midnight.

### Charges look wrong

Charge = the selected Billing Profile rate × the effective multiplier. Check the Provider default Profile and multiplier. Then check the model Profile and multiplier overrides.

## Streaming problems

### The stream stops mid-response

Monoize never switches upstreams after the first response byte. A stream that dies mid-response reflects an upstream failure. Read the log row and enable capture to see the raw upstream frames.

### A client rejects long SSE frames

Some clients limit SSE frame length. Add the `stream_split_sse_frames` transform to the serving Provider. See [Stream: split oversized SSE frames](/en/docs/transforms/stream_split_sse_frames).

### A client reports a transport decode error after a long reasoning phase

The error text is `Transport error: error decoding response body`. Monoize sends `Cache-Control: no-cache` and `X-Accel-Buffering: no` on every SSE response. A reverse proxy that still buffers or compresses `text/event-stream` can truncate the stream. Disable proxy buffering for the Monoize location. In nginx, set `proxy_buffering off`. Verify the proxy does not gzip the event stream.

### The upstream requires streaming

Add the `stream_force` transform to force `stream: true` toward the upstream. Monoize still returns a non-streaming response to the client when the client asked for one.

## Protocol conversion questions

### `400 empty_input_after_conversion`

Send a non-empty message or the complete conversation history. This error means no messages remain for the available Chat Completions or Responses Channel after conversion.

Include the matching tool call when you send a tool result through Chat Completions. Use `previous_response_id` or `conversation` only with a Responses upstream that supports that state. Monoize preserves these references and saved `prompt` objects for a Responses upstream.

Monoize skips an empty Channel payload and checks the remaining Channels. If all payloads are empty, it returns this error without calling an upstream or selecting another model. Streaming requests receive an error event. This check cannot recover missing history. Enable request capture before reproducing the failure to locate any content loss.

### `400 invalid_request` with `does not support thinking.type=adaptive`

The full message is `Messages model <name> does not support thinking.type=adaptive`. Monoize validates every encoded Messages request before dispatch. It returns this error and calls no upstream.

Claude Code sends `thinking: { "type": "adaptive" }` in its `/v1/messages` requests. Monoize preserves that object for a `messages` upstream. The upstream model name must denote an adaptive Claude model. The lowercased name must contain `claude`, or start with `opus-`, `sonnet-`, or `haiku-`. A name such as `DeepSeek/DeepSeek-V4-Pro` fails this test, so validation rejects the request.

Apply one of these fixes:

1. **Send the model over Chat Completions.** Set the Channel type to `chat_completion`. Alternatively, add an **API Type Overrides** rule on the Provider that maps the model pattern to `chat_completion`. The rule pattern matches the logical model name from the client, not the `redirect` target. Monoize then encodes the reasoning controls of the upstream model family.
2. **Redirect Claude model names to Claude models only.** Read the Channel model mapping. A `redirect` that points an adaptive Claude name at another model family keeps the client's Claude-specific controls in the request. See [Providers and Channels](/en/docs/dashboard/providers-and-channels).
3. **Disable extended thinking in the client.** A request with no `thinking` object passes validation for a non-Claude model. A request with `thinking.type=disabled` also passes.

The mirror case returns `does not support thinking.type=enabled; use adaptive`. It occurs when the client sends a manual `budget_tokens` and the upstream model is Opus 4.7 or later, Sonnet 5 or later, Fable 5, or Mythos 5. The same fixes apply.

### Reasoning disappears after conversion

Some upstreams return reasoning in nonstandard fields. Use the reasoning transforms to restore or reshape it. Start with [Transforms](/en/docs/transforms).

### Provider-specific fields are missing upstream

Cross-family conversion removes provider-specific nested fields with no safe target representation. Use the `field_set` transform to reinstate a field for one Provider.

### A client rejects tool-call numbers such as `4338.0`

Some upstreams emit whole numbers as JSON floats in tool-call arguments. Codex `write_stdin` parses `session_id` as an integer and rejects `4338.0`. Monoize rewrites integer-valued floats in tool-call arguments to JSON integers before the client receives them. You do not need a transform rule for this rewrite.

## Dashboard access

### Lost admin password

Another `super_admin` can reset it in **Users**. When no `super_admin` remains, reset it directly in the database.

### First account is not admin

The first registered account becomes `super_admin`. This rule applies once. Later accounts default to `user`.
