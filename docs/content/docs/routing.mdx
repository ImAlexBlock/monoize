## Route selection

For each request, Monoize resolves the route in this order:

1. **Model redirects.** API-key rules run first, then global rules. The first match rewrites the model name.
2. **Provider selection.** Monoize collects enabled Providers whose Group is allowed by the API key and whose embedded Channel maps the model with complete pricing.
3. **Channel selection.** Each Provider owns one embedded Channel. Monoize uses that Channel when it is enabled and healthy.

## Retry and fallback

Monoize tries the selected Provider's Channel, then falls forward to the next Provider in the same Group.

- Each Channel gets `channel_max_retries + 1` attempts. The default is 1 attempt, no in-Channel retry.
- `channel_retry_interval_ms` inserts a wait between in-Channel retries. The default is `0`.
- When a Provider is exhausted, Monoize continues with the next eligible Provider.
- When all Providers are exhausted, the client receives HTTP `502` with code `upstream_error`.

### Which errors retry the same Channel

| Error | Same-Channel retry | Advance to next route |
| --- | --- | --- |
| HTTP `408`, `429`, `5xx` | Yes | Yes, after Channel budget |
| Timeout, connection refused or reset | Yes | Yes, after Channel budget |
| Other upstream errors (for example `400`, `401`, `404`) | No | Yes, at once |
| Monoize-side errors (auth, balance, validation, billing) | No | No; routing stops |

### Fallback to the key's recent model

When every route for the requested model fails before any output, or no route exists, Monoize retries the request once with a different model.

- The fallback model is the model of the API key's most recent successful request in the last 24 hours, other than the requested model.
- Monoize does not retry when the key has no such request, when the key's model limits exclude that model, or when the client has disconnected.
- The retry does not fall back again. Monoize bills the retry at the fallback model's price.
- Request Logs show two rows: the failed request and the retry. The retry's request ID ends with `-fallback`.

This keeps client helper tasks working. For example, Codex requests `gpt-6-luna` for thread titles. If no route serves that model, the request uses your main model.

## Streaming guarantee

Fallback ends when the first response byte reaches the client. Before that byte, Monoize can switch Channels and Providers freely. After that byte, Monoize never switches. A visible stream therefore always comes from one generation.

## Streaming timeouts

Use `monoize_stream_idle_timeout_ms` to limit waiting between upstream stream events. The default is `120000` milliseconds.

Monoize limits the wait for response headers to ten times the effective `request_timeout_ms`, with a minimum of `600000` milliseconds.
An upstream HTTP error body shares that deadline.
After successful headers, an active stream has no total lifetime limit.
This rule also covers image streams and upstream streams collected into a non-streaming response.
Non-streaming upstream requests retain their total request timeout.

## Circuit breaker

Each Provider has `circuit_breaker_enabled`. When enabled:

- A Channel becomes unhealthy after `failure_count_threshold` retryable failures (default `3`) within `window_seconds` (default `30`).
- An unhealthy Channel is skipped for `cooldown_seconds` (default `60`). Failures caused by HTTP `429` use `rate_limit_cooldown_seconds` (default `15`).
- With `per_model_circuit_break` on, health is tracked per `(Channel, model)` pair instead of per Channel.
- With active probing on, Monoize probes cooled-down Channels in the background and restores them after the success threshold.

Set `circuit_breaker_enabled` to `false` on a Provider to ignore health state for it. Passive breaking and active probing then stop for that Provider.

## Session affinity

Monoize can bind a conversation to the Channel that served it, so follow-up requests with server-side state (for example Responses `previous_response_id`) reach the same upstream. Affinity is configured globally and per Channel. An affinity-preferred Channel still obeys eligibility and health rules.

## Timing metrics

Every request row in [Request Logs](/en/docs/request-logs) records total duration, time to first byte, and visible-output tokens per second. Use these values to compare Providers before you change Group priority.
