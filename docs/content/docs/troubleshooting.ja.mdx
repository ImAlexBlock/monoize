## まずログを確認する

設定を変更する前に、ダッシュボードの**ログ**を開きます。失敗した各リクエストの行には、エラーコード、HTTP ステータス、失敗した上流試行がすべて表示されます。[リクエストキャプチャ](/ja/docs/request-logs)を有効にすると、上流の正確なペイロードを検査できます。

## 認証エラー

### `401 unauthorized`

1. キーが `sk-` で始まり、完全であることを確認します。
2. **トークン管理**で、キーが有効で期限切れでないことを確認します。
3. キーの所有ユーザーアカウントが有効であることを確認します。
4. ヘッダー形式を確認します: `Authorization: Bearer sk-...` または `x-api-key: sk-...`。

### `403 model_not_allowed`

キーのモデル制限が有効で、要求モデルがどのエントリとも一致していません。正確な論理モデル名をキーのモデルリストに追加するか、モデル制限を無効にします。

### `403 ip_not_allowed`

クライアント IP がキーの IP ホワイトリストにありません。アドレスまたは CIDR 範囲を追加するか、ホワイトリストを空にします。Monoize がリバースプロキシの背後にある場合は、プロキシが実際のクライアント IP を転送していることを確認します。

## ルーティングエラー

### `502 upstream_error`

適格なルートがすべて失敗したか、モデルを提供するルートがありません。次の順序で確認します。

1. **ルートが存在しない。** 有効な Provider に有効な Channel があり、完全な Billing Profile でモデルが対応付けられていることを確認します。
2. **グループが交差しない。** キーのグループは Provider と少なくとも 1 つのグループを共有する必要があります。[API キー](/ja/docs/dashboard/api-keys)を参照してください。
3. **すべての Channel が不健全。** サーキットブレーカーはクールダウン中の不健全な Channel をスキップします。ログ行の失敗試行を読み、根本の上流エラーを特定します。
4. **倍率上限。** `max_multiplier` を設定したキーは、上限を超える価格のモデルエントリをスキップします。

## 課金エラー

### `402 insufficient_balance`

ユーザー残高、またはキーのサブアカウント残高がゼロ以下です。**ユーザー**で残高を追加してください。独立残高を持つ既存キーは残高が尽きるか削除されるまでその残高から課金されます。新しいキーにサブアカウントオプションはありません。

### `402 api_key_spend_limit_reached`

キーの利用上限ウィンドウを使い切りました。キーの編集ダイアログで上限を引き上げるか空欄にしてください。時間ウィンドウは継続的にロールオーバーし、日次ウィンドウは UTC の午前0時にリセットされます。

### 課金額がおかしい

課金額 = 選択した Billing Profile のレート × 有効な倍率です。Provider の既定 Profile と倍率を確認します。次にモデルの Profile と倍率の上書きを確認します。

## ストリーミングの問題

### ストリームが途中で止まる

最初のレスポンスバイト以降、Monoize は上流を切り替えません。途中で切れたストリームは上流の障害を反映しています。ログ行を読み、キャプチャを有効にして上流の生フレームを確認します。

### クライアントが長い SSE フレームを拒否する

一部のクライアントは SSE フレーム長を制限します。処理する Provider に `stream_split_sse_frames` 変換を追加します。[ストリーム: 長大 SSE フレームの分割](/ja/docs/transforms/stream_split_sse_frames)を参照してください。

### 長い推論フェーズの後にクライアントが転送デコードエラーを報告する

エラー文は `Transport error: error decoding response body` です。Monoize はすべての SSE レスポンスに `Cache-Control: no-cache` と `X-Accel-Buffering: no` を送信します。それでも `text/event-stream` をバッファまたは圧縮するリバースプロキシはストリームを切り捨てる可能性があります。Monoize の location でプロキシバッファリングを無効にします。nginx では `proxy_buffering off` を設定します。プロキシがイベントストリームを gzip していないことを確認します。

### 上流がストリーミングを必須とする

`stream_force` 変換を追加して、上流へ `stream: true` を強制します。クライアントが非ストリーミングを要求した場合でも、Monoize はクライアントに非ストリーミングのレスポンスを返します。

## プロトコル変換に関する質問

### `400 empty_input_after_conversion`

空でないメッセージ、または会話履歴全体を送信してください。このエラーは、変換後に利用可能な Chat Completions または Responses Channel へ送信するメッセージが残っていないことを示します。

Chat Completions でツールの結果を送信する場合は、対応するツール呼び出しも含めてください。`previous_response_id` と `conversation` は、サーバー側の状態をサポートする Responses 上流で使用してください。Monoize は Responses 上流にこれらの参照と保存済みの `prompt` オブジェクトを転送します。

Monoize はメッセージが空の Channel をスキップし、残りの Channel を確認します。すべてが空の場合、上流を呼び出さず、モデルも変更せずにこのエラーを返します。ストリーミングリクエストにはエラーイベントを返します。この確認では欠落した履歴を復元できません。内容の欠落箇所を調べるには、再現前にリクエストキャプチャを有効にしてください。

### `400 invalid_request` が `does not support thinking.type=adaptive` を返す

完全なメッセージは `Messages model <名称> does not support thinking.type=adaptive` です。Monoize は送信前にエンコード済みの Messages リクエストを検証します。このエラーを返し、上流を呼び出しません。

Claude Code は `/v1/messages` リクエストで `thinking: { "type": "adaptive" }` を送信します。Monoize は `messages` 上流向けにそのオブジェクトを保持します。上流のモデル名は adaptive 対応の Claude モデルを示す必要があります。小文字化した名前が `claude` を含むか、`opus-`、`sonnet-`、`haiku-` で始まる必要があります。`DeepSeek/DeepSeek-V4-Pro` のような名前はこの条件を満たさないため、検証はリクエストを拒否します。

次のいずれかの方法で修正します。

1. **そのモデルを Chat Completions で送信する。** Channel のタイプを `chat_completion` に設定します。または Provider に **API タイプオーバーライド** のルールを追加し、そのモデルパターンを `chat_completion` にマッピングします。ルールのパターンはクライアントが送信した論理モデル名に一致します。`redirect` 先には一致しません。Monoize は上流モデルファミリーの推論制御フィールドをエンコードします。
2. **Claude のモデル名は Claude モデルにのみリダイレクトする。** Channel のモデルマッピングを確認します。adaptive 対応の Claude 名を別のモデルファミリーへ `redirect` すると、クライアントの Claude 固有の制御フィールドがリクエストに残ります。[Provider と Channel](/ja/docs/dashboard/providers-and-channels) を参照してください。
3. **クライアントで拡張思考を無効にする。** `thinking` オブジェクトを含まないリクエストは、Claude 以外のモデルでも検証を通過します。`thinking.type=disabled` を含むリクエストも通過します。

対称のケースは `does not support thinking.type=enabled; use adaptive` を返します。クライアントが手動の `budget_tokens` を送信し、上流モデルが Opus 4.7 以降、Sonnet 5 以降、Fable 5、または Mythos 5 の場合に発生します。修正方法は同じです。

### 変換後に推論内容が消える

一部の上流は非標準フィールドで推論内容を返します。推論系の変換ルールで復元または整形します。[変換ルール](/ja/docs/transforms)から始めてください。

### プロバイダー固有フィールドが上流に届かない

プロトコルファミリーをまたぐ変換は、安全な対応先のないプロバイダー固有のネストフィールドを除去します。`field_set` 変換で特定の Provider にフィールドを再設定します。

### クライアントがツール呼び出しの `4338.0` のような数値を拒否する

一部の上流は、ツール呼び出し引数の整数を JSON 浮動小数点で返します。Codex の `write_stdin` は `session_id` を整数として解析し、`4338.0` を拒否します。Monoize はクライアントへ返す前に、ツール呼び出し引数内の整数値浮動小数点を JSON 整数へ書き換えます。この書き換えに変換ルールは不要です。

## ダッシュボードへのアクセス

### 管理者パスワードを紛失した

別の `super_admin` が**ユーザー**でパスワードをリセットできます。他に `super_admin` がいない場合は、データベースで直接リセットします。

### 最初のアカウントが管理者にならない

最初に登録したアカウントが `super_admin` になります。このルールは一度だけ適用されます。以降のアカウントのデフォルトは `user` です。
